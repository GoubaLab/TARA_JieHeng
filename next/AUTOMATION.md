# 确定性自动分析

在项目中打开「自动分析」。服务根据已保存的架构、通信、操作系统、安全属性和资产关联，生成解释明确的分析候选。此流程完全在本地运行，不配置模型也能使用。

## 操作流程

1. 保存架构并核对自动资产；手工资产需明确关联节点和安全属性。
2. 刷新候选，查看命中事实、适用前提、需要核对的控制和已有分析。
3. 选择适用候选，填写责任人并确认审阅。平台先保存还原点，再一次性生成损害场景、威胁与路径、验证需求。
4. 在风险分析中补充实际影响、可行性、CAL 和依据；继续目标、风险处置、需求验证和报告流程。

候选不表示存在漏洞或缺失控制；保护属性表示需求，不代表控制已实施。自动生成记录保持未评分，不编造验证结果、接受决定或签名。缺少准确资产关联或有歧义时不能采用，应先完善资产。

## 当前原创规则

| 规则 | 触发依据 |
| --- | --- |
| DF-TRUST-INPUT | 一端为外部实体，或两端显式信任域不同 |
| DF-WIRELESS-INTEGRITY | 无线介质或已登记的无线协议 |
| IF-DEBUG-ACCESS | JTAG、DAP、SWD、UART；实际调试用途仍需核实 |
| OS-NETWORK-SURFACE | 已登记的操作系统与网络连接；不据 OS 名称认定 CVE |
| DS-CONFIDENTIALITY | 存储和准确关联的保密需求资产 |
| DF-FRESHNESS | 通信显式声明新鲜性需求 |
| DF-AVAILABILITY | 通信显式声明可用性需求 |
| SW-UPDATE-INTEGRITY | 用途字段包含软件/固件更新标识，实际承载内容待核对 |

信任域使用实体属性 `trust_zone` 或「信任域」。当前不从矩形框的视觉位置推断安全边界归属，避免拖动图元改变安全事实。电能流不参与数据流规则。

## 一致性与追溯

候选 ID 由规则和对象身份决定；规则版本为 `jieheng.automation/1`。计划摘要包含模型语义与相关工作产品，不包含坐标、线段、箭头或标签位置。API 同时检查项目修订和计划摘要，因此即使只调整布局，采用旧页面前仍需刷新到当前修订。

采用时固定保存候选的事实、前提与控制检查快照，并使用幂等键、事务、还原点和审计记录；已有同源场景不重复创建，不覆盖人工记录。相似手工分析会提示核对；相同来源标记或等价标题视为已有覆盖。新增工作产品携带 `AUTO:` 来源标记，Excel/HTML 增加「自动化分析追溯」。

当前规则不自动认定 CVE 适用，不执行攻击验证，不根据新知识改写旧结论。已采用候选的前提变化仍需人员复核；专门的变更影响待办列入产品路线图。

## 开发接口

- `GET /api/v1/workspaces/{id}/automation-plan`：读取候选、版本、摘要及匹配上下文。
- `POST /api/v1/workspaces/{id}/automation-adoptions`：提交 `plan_hash`、`candidate_ids`（1–50）、`owner`、`reviewed:true`，并携带 `If-Match` 和 `Idempotency-Key`。
- 写入规则与统一错误遵循 [API 约定](API_CONVENTIONS.md)。规则实现和匹配测试位于 `server/internal/assurance/automation_rules.go` 与对应测试。

规则是本项目原创工程检查，未复制商业产品规则或历史私有资料。后续扩展优先采用可验证的结构化事实和受限声明式条件，不开放任意代码求值。
